# 多算法切换第一步：帧边界控制器

本步只验证模式请求与帧边界行为，对应验收要求 B5 的控制部分。新增 `frame_mode_ctrl.v`、`tb_frame_mode_ctrl.v` 和 `check_frame_mode_ctrl.py`，没有修改已有图像 RTL。尚未接通四路图像，不代表 B5 整层验收通过。

## 模式与接口

| 模式 | 后续对应画面 |
|---|---|
| 0 | 基础 RGB 原图 |
| 1 | 灰度 |
| 2 | Sobel 边缘 |
| 3 | 分割掩膜，0 黑、1 白 |

`clk` 上升沿采样，`rst_n` 低有效异步复位。`in_valid && in_sof` 是有效帧首事件，应来自已接纳的合法视频流。控制器不生成坐标，不读取 RGB，也不负责丢弃残帧；它仅根据有效 SOF 更新模式。

`mode_req_valid` 为同一时钟域内的请求使能，`mode_req[2:0]` 为请求值。0～3 合法，4～7 非法；特意保留第三位以便表示和测试非法值。每个请求拍都会采样，推荐事件源发一拍脉冲。外部按键同步、去抖、跨时钟域传递不属于本步，后续单独实现。

规则：

1. 复位后 `active_mode=0`，pending 清空。
2. 合法请求先写入 pending，同一帧多个合法请求取最后一个。
3. 下一有效 SOF 采用此前 pending，整帧 `active_mode` 保持不变。`in_valid=0` 时即使 SOF=1 也不能提交。
4. 请求与 SOF 恰好同拍时，该 SOF 先采用旧 pending；同拍新请求留给再下一 SOF。避免边界含糊。
5. 非法请求不改变 active 或此前合法 pending，并在采样后令 `invalid_request=1`。下一拍无非法请求时清零；连续非法请求期间保持 1。没有 pending 时保持当前模式；已有 pending 时，下个 SOF 仍可执行此前合法请求。
6. 无请求使能时忽略请求总线的值。

`active_mode[1:0]` 是在 SOF 采样沿之后更新的寄存器输出。若下游也在该沿用寄存器记录首像素，必须使用组合输出 `mode_for_sof`，才能给新帧标上本次应采用的模式。它在 SOF 以外只是下一帧模式预览，不能当成当前像素的模式；异步复位后两者均为 0。

本模块不处理数据路径，所以没有所谓“图像延迟一拍”。控制输出的时序是请求采样后进入 pending，在后续有效 SOF 采样沿之后更新 active。
